# BL-14.3.1 — Dynamic Boolean routing development pilot

Status: **IMPLEMENTED / NON-FINAL DEVELOPMENT; HARDWARE CLAIMS FORBIDDEN**

This slice advances BL-14 from frozen structured masks toward input-conditioned sparsity without replacing the numerical model. It reuses the already-declared BL-14.2.2 synthetic `ReLU` workload and its disjoint TRAIN / SEARCH / non-final VALIDATION partitions.

## Question

Can a minimal input-conditioned Boolean controller select between two exact 4/8 Boolean-derived unit masks on SEARCH, freeze that pair, and preserve a better task-quality / reference-work trade-off on the existing non-final VALIDATION panel than matched static and dynamic controls?

This is a development question. The reused panel has already been observed in BL-14.2.2/BL-14.2.3 and is not an untouched holdout.

## Frozen controller family

The only dynamic predicate in this version is

```text
route_nonnegative(x) = (x[0] >= 0)
```

For each trial, the existing BL-14.2.2 Boolean topology family supplies exact 4/8 candidate masks. SEARCH chooses one candidate for `route_nonnegative = false` and one for `true`, with deterministic mask-code tie breaking. Thus the deployed decision is equivalent to

```text
keep(unit, x) =
    (route_nonnegative(x) AND F_nonnegative(unit_predicates))
    OR
    (NOT route_nonnegative(x) AND F_negative(unit_predicates))
```

where each `F_*` is an already materialized BooleanLab truth-table candidate whose exact mask is revalidated before scoring.

All twelve trial controllers are frozen before any VALIDATION batch is constructed. No VALIDATION value can alter the fitted numerical weights, Boolean candidate population, route predicate, selected branch masks, random controls, or tie rule.

## Matched controls

Every routed sparse mask retains exactly 4 of 8 units. The report keeps these controls on the same numerical workload:

- dense;
- magnitude 4/8;
- unit-level 2:4;
- activation-energy 4/8;
- four deterministic static random 4/8 masks;
- the best frozen static Boolean 4/8 mask from the existing SEARCH contract;
- a dynamic random pair of deterministic 4/8 masks using the same `x[0] >= 0` route predicate;
- the dynamic Boolean pair.

The dynamic Boolean branch search evaluates the same Boolean candidate-mask population on the two disjoint SEARCH partitions. Across both partitions, each candidate is scored on every SEARCH sample exactly once; this preserves the candidate-sample scoring budget of the static Boolean scan. It does **not** establish equal controller-construction time, enumeration cost, memory traffic, compilation cost, or hardware cost.

## Execution accounting

Admission occurs before projection, `ReLU`, and readout contribution through the existing BL-14.2.2 `predict` path. The dynamic report keeps separate fields for:

- task MSE;
- dense reconstruction MSE;
- reference multiplication count;
- reference `ReLU` count;
- mask tests;
- raw-input controller predicate tests;
- route-mask switches between consecutive samples.

The last five are deterministic reference counters. They are not elapsed time, bandwidth, memory-residency, energy, or hardware utilization measurements. A hardware-performance claim requires a later protocol that measures controller time and downstream time separately on declared hardware.

## Reproduce the development report

```bash
set -euo pipefail
if [ ! -f Cargo.lock ]; then cargo generate-lockfile; fi
cargo run --locked -p booleanlab-discovery --bin bl14_structured_relu --release -- --dynamic-routing-v1
```

The exact source commit, resolved lockfile, compiler identity, raw report, replay hash and CI run must be retained before interpreting numerical output. Until that evidence exists, this document defines implementation and protocol only; it does not state a numerical result.

## Interpretation limits

This pilot does not establish a Boolean advantage, quality preservation, model generalization, reduced memory traffic, lower energy, or speedup. It uses a small synthetic model and a reused development panel. Any equal, worse, unstable, or route-degenerate outcome is retained as evidence. Promotion to SciRust, ElasticXxx, FLAT-ATTENTION, KVLab, NNIS or Forge requires a separate versioned contract and evidence appropriate to that repository.
